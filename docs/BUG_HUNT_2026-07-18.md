## P0 — broken in committed code, user-visible at runtime

### M-1 · Mobile Today tab crashes rendering the Gowri card
`mobile/app/(tabs)/today.tsx:1031` — `GowriCard` is a top-level component but calls
`fmt(slot.start)` / `fmt(slot.end)`; `fmt` is a `const` defined at line 264 *inside* the
main screen component, so it is not in `GowriCard`'s scope. The card is rendered at
line 639 whenever `primaryGowri` is truthy — i.e. on every successful Today-tab load
that has a Gowri slot → `ReferenceError` on the app's home screen.

- The `fmt` uses at lines 634/647 are fine (closures inside the parent); only the
  extracted component body is broken.
- Committed code (file last touched 2026-07-04); survived because mobile tsc was
  already red (M-2), so nothing gated it.
- **Fix:** use the module-level `formatTime` (line 95), or thread `fmt`/`lang` through
  props like `isTamil` already is.

### B-2 · Prasna casts the chart from server wall-clock labeled as user-local time
`app/api/prasna.py:24` — `question_dt = payload.question_datetime_local or datetime.now()`.
`cast_prasna_chart` (`app/calculations/prasna.py:51-52`) interprets a naive datetime as
wall-clock **in `payload.timezone_name`**. The fallback is *server*-local `now()`, so the
server's wall-clock gets relabeled as the user's timezone.

- No client ever sends `questionDateTimeLocal` (the shared wrapper marks it optional,
  "defaults to now on the server"; zero web/mobile call sites populate it) — so the
  fallback is the **only** path in practice.
- Invisible on the IST dev box (server tz == user tz). On a UTC-hosted server an IST
  user's prasna moment is 5.5 h off → prasna lagna wrong by ~2–3 rasis, wrong
  Moon nakshatra possible. Same silent-domain-error class as the past calc bugs.
- **Fix (server-side, no client change needed):**
  `datetime.now(ZoneInfo(payload.timezone_name)).replace(tzinfo=None)` as the fallback.

## P1 — real defects in the uncommitted reasoning-depth diff

### B-1 · Marriage score drops Venus affliction exactly when Venus is the 7th lord
`app/services/marriage_service.py` (new affliction block in `assess_marriage_prediction`):

```python
if affliction.karaka_afflicted_by or (seventh_lord != "VENUS" and affliction.lord_afflicted_by):
```

For **Aries and Scorpio lagna**, Venus is both 7th lord and karaka. In that case
`bhava_afflictions` deliberately skips `karaka_afflicted_by` (karaka == lord), and the
second clause explicitly excludes Venus-as-lord — so a heavily afflicted Venus produces
**no penalty and no challenge line** for precisely the charts where Venus matters twice.
The promise gate above still catches the ≥2-malefic case
(`len(affliction.lord_afflicted_by) >= 2`), but the score path is silently optimistic.

- **Fix:** `if affliction.karaka_afflicted_by or affliction.lord_afflicted_by:` and pick
  the display target as karaka-name when `seventh_lord == "VENUS"` (the
  `lord_afflicted_by` tuple *is* Venus's afflictors in that branch).

### W-1 · Raw machine tokens now render on Life Area cards (English leaks into Tamil UI)
`app/services/life_areas_service.py:1310` pushes the new connection strings
(`maha:VENUS:lords_bhava`, `antar:RAHU:node_agent_of_VENUS`, …) into
`supporting_factors`, and lines 1318-1326 add new keys
(`SATURN_occupies_house`, `SATURN_aspects_house`, `papa_kartari_hems_house`,
`shubha_kartari_protects_house`). The web renderer
(`web/components/life-area-card.tsx`, `humaniseFactorKey`) has **no rule for the
colon format** — it falls through to `key.replaceAll("_", " ")` → users see
"+ maha:VENUS:lords bhava". The new snake_case keys are also missing from
`FACTOR_LABELS`, so Tamil users get raw English fragments ("papa kartari hems house").
Because `dasha_activates_area` is appended immediately before the connection strings,
the tokens reliably occupy the visible top-3 slots.

- **Fix options:** (a) don't ship the raw connection strings in `supporting_factors`
  (keep them in a debug/detail field), or (b) teach `humaniseFactorKey` the
  `level:PLANET:kind` format and add the four new keys to `FACTOR_LABELS` (ta + en).
  Note mobile renders these factors too — check its formatter if going route (b).

## P2 — moderate

### W-2 · Wrong weekday principle for negative-UTC users
`web/components/dashboard-hero.tsx:569` —
`DAILY_PRINCIPLES[new Date(selectedDate).getDay()]` where `selectedDate` is a
date-only string. `new Date("2026-07-18")` parses as **UTC midnight**; `.getDay()`
reads **local** time → in the Americas the previous weekday is returned. IST users
unaffected; diaspora users get the wrong day's principle text.
- **Fix:** parse parts (`const [y,m,d] = selectedDate.split("-").map(Number);
  new Date(y, m-1, d).getDay()`), or anchor at noon: `new Date(selectedDate + "T12:00:00")`.
